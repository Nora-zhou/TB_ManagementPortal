01先纠正上一版的错误

我在不知道这个项目存在的前提下，让你从零写浏览器层。现在看这是明显的浪费。

rpa/browser.py 那 722 行里，解决的是淘宝自动化的全部真问题，而且注释里保留了踩坑过程：

已经解决的问题如果重写会发生什么
SPA 门户登录态渲染慢，DOM 判定会误判为未登录你会写成「一连就判断没登录」，然后反复重新登录，触发风控
淘宝 SSO 授权链（登录页 → 授权确认 → 门户）走不完会退回登录页你会卡在「明明登录成功为什么又跳回登录页」，至少耗掉一个周末
登录表单嵌在 iframe / 弹窗新标签页里你会找不到输入框，然后怀疑选择器写错
三种浏览器模式（独立 profile / 系统 profile / CDP）你会重复踩 profile 被占用的坑
验证码检测 + 人工接管等待机制你会先做成全自动，然后账号被限制
多标签页管理（不误关用户已开的标签）CDP 模式下你会把用户浏览器关掉
这 16 小时的复用不只是省时间，是省掉一次失败。浏览器自动化是这类工具里唯一「不是靠努力能解决」的部分，它靠的是反复的线上调试。你已经付过这笔学费了。

03一个被你自己忽略的战略资产：真实利润数据

这是我在读代码时才发现的，比复用浏览器层更重要。

这个仓库里已经打通了一条几乎所有店铺诊断工具都做不到的链路：

数据来源能算出什么
买家实付 / 退款SubOrder（订单 Excel 导入）真实收入口径
1688 采购成本PurchaseOrder实际进货成本
SKU 级成本ProductSKUCost单品毛利
平台扣费 / 推广费StorePlatformExpense（RPA 抓的）真实费用

四者相减 = 真实净利润。这意味着你的检测报告可以多一个维度，而这个维度市面上没人能提供：

「利润健康度」维度：真实毛利率 = （买家实付 − 退款 − 采购成本 − 平台费 − 推广费）÷ 买家实付；
盈亏平衡 ROI = 1 ÷ 真实毛利率。
拿你自己的店举例：毛利率 40% → 平衡 ROI = 2.5，当前 ROI 2.39 → 结论是「在盈亏平衡线以下」。这句话任何只能看公开数据的工具都说不出来。

这直接决定产品可以分两档卖

档位需要客户提供能回答的问题定价
基础版
公开数据检测		只要店铺链接你的页面/素材/结构有什么问题¥299–899
利润版
经营数据检测		订单导出 + 采购成本 + 后台授权你到底赚不赚钱，哪个 SKU 在亏¥1,499–2,999

基础版谁都能做，是引流品。利润版是你的护城河——因为你有 RPA 能自动抓平台费和推广费，代运营公司都没有这个能力。而且客户一旦把成本数据交给你，迁移成本极高。

利润版涉及客户敏感经营数据，必须先签保密约定，且数据只落本地不外传。这一档建议等基础版跑通 3–5 家、你确认了交付流程之后再做，不要一开始就上。

一个关键的工程决策：商品页采集用独立 profile

商品详情页是公开页面，不需要登录。这是整个检测模块风险最低的一点，也是最容易被做错的一点：

  • 用独立的 browser profile（甚至 headless=True），与千牛/阿里妈妈的账号 profile 完全隔离；
  • 绝不共用千牛的登录态去访问公开商品页 —— 一旦被关联，你的店铺主账号会被牵连；
  • 商品页采集不产生登录行为，也就不触发验证码，可以安心跑批量。

只有「利润版」需要客户授权后台数据时才动登录态，那属于第二阶段。

新增的 6 张表

-- 事实层：只增不改
CREATE TABLE inspection_run (
  id INTEGER PRIMARY KEY,
  store INTEGER NOT NULL,
  subject TEXT NOT NULL,          -- self | client | competitor
  subject_name TEXT,
  run_id TEXT NOT NULL UNIQUE,
  scope TEXT,                     -- shop | item
  item_target INTEGER, item_success INTEGER,
  status TEXT NOT NULL,           -- running | ok | partial | failed
  started_at TEXT, finished_at TEXT
);

CREATE TABLE item_snapshot (
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL,
  item_id TEXT NOT NULL,
  title TEXT, price_cents INTEGER,
  image_count INTEGER, image_urls TEXT,   -- JSON
  detail_image_count INTEGER, detail_text TEXT,
  sales_text TEXT, sales_parsed INTEGER,
  review_count INTEGER, rating REAL,
  raw_path TEXT,                  -- 原始响应存档
  reliable INTEGER DEFAULT 1,
  collected_at TEXT NOT NULL
);

CREATE TABLE assertion_result (
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL, item_id TEXT,
  rule_id TEXT NOT NULL,          -- PRICE_POSITIVE / IMAGE_COUNT_MIN ...
  passed INTEGER NOT NULL,
  actual TEXT, expected TEXT, message TEXT
);

-- 判定层：可重算
CREATE TABLE metric (
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL, scope TEXT, scope_key TEXT,
  name TEXT NOT NULL,
  value REAL, baseline REAL, baseline_type TEXT,
  deviation REAL, level TEXT      -- normal | watch | alert
);

CREATE TABLE score (
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL, scope TEXT, scope_key TEXT,
  dim TEXT NOT NULL,              -- material|title|detail|price|review|traffic|profit
  points REAL, max_points REAL,
  evidence TEXT,                  -- JSON 明细
  rule_version TEXT NOT NULL
);

CREATE TABLE inspection_report (
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL UNIQUE,
  total_score REAL, grade TEXT,
  html_path TEXT, pdf_path TEXT,
  template_ver TEXT, generated_at TEXT
);
注意 score.rule_version 和 事实层/判定层的分离。改了评分规则后，可以对历史所有 run 重新打分做回归——这是测试工程师做产品应有的自觉，也是别人做不到的。

08两个闸门与止损点

GATE 01（I1 后，第 3 周）：采集数据不准就停。若商品页采集反复不稳定（改版、字段缺失、反爬），立刻切降级方案：手工导出 Excel / 手工填表 → 工具只做「进 → 出报告」。这条路一样能交付客户、一样能验证需求，而且 20 小时就能上线。不要为了提高自动化率把项目卡死。
止损点二（I4 后，第 6 周）：如果评分卡结果与你的经验判断差距始终很大，重写 rubric，不要改代码迁就。评分卡错了，后面每一份报告都是错的，而报告是你唯一交付物。

不要做的事

看似有用的东西为什么先不做
检测功能的 Vue 页面CLI + PDF 已能服务前 5 个客户。等有付费客户了再决定界面长什么样
把浏览器层重构成「可插拔 adapter」现有实现能跑就行。抽象要等到有第二个数据源时再做
多平台（京东/拼多多/抖音小店）一个平台做透，比四个平台都半成品值钱
实时监控大屏月度订阅只需要每月一份 PDF，不需要实时
客户自助上传后台数据（利润版）第二阶段。先用手工方式交付 3 家，确认有人愿意为它付 ¥1499

09两个方案对比

维度原方案（新建 StoreLens）新方案（改造 spec-kit-app）
工时66 h59 h
浏览器层风险高——XHR 拦截 + 登录从未验证低——browser.py 已实战验证
I1 超支可能12h 可能变 25h+较小，10h 预算较实
数据积累从零开始直接继承两店历史订单与成本
产品差异化只有公开数据可做利润版（真实净利），别人做不到
技术债无（新项目）需先还 4h（D0）
耦合风险无需隔离客户端数据，注意不污染主账号登录态
前端不做可低成本复用现有 RPA 任务页的模式
结论：新方案工时更少、风险更低、产品天花板更高。唯一的代价是必须先花 4 小时还技术债，以及接受「一个仓库同时装自用工具和对外服务」的耦合——但检测模块是独立目录 + 独立 CLI，实际耦合很轻。
